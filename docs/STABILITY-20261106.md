# localhost 连接与重启稳定性验证

2026-11-06，在本机真实 SYSTEM 服务及登录用户助手上测试。最终证据：`artifacts/reconnect-2026-11-06T01-58-15-278Z/report.json`。测试使用独立 localhost TCP 转发端口，客户端与服务端之间仍是原证书加密连接；未禁用网卡、修改防火墙或断开其他应用网络。

| 场景 | 最终结果 |
|---|---|
| 连续 3 轮连接中断，每轮约 700 ms | 设备列表观察到 offline → online，原凭据自动认证；长 shell 恢复查询并成功完成，标记文件确认只执行一次 |
| 终止精确核验过的 Node 服务进程 | 宿主约 2 秒后启动新 Node；CLI 自动重连，设备 UUID 不变，未完成测试任务为 unknown / SERVICE_RESTARTED |
| 终止精确核验过的 WdbService 服务宿主 | Windows SCM 自动恢复；最终复验覆盖第三档 30 秒延迟，新的宿主与 Node PID 均改变，CLI 在默认 60 秒恢复窗口内自动重连 |
| 重启时任务状态 | 未完成任务保持 unknown，不自动执行；已落盘完成的任务保持原成功结果 |
| 任务接受回包丢失 | 自动回归模拟服务接受后销毁响应连接，客户端恢复得到同一个 taskId；服务仅有一条任务，不重复执行 |
| 证书 / deviceId 改变、授权撤销 | 自动回归立即停止重试，不自动信任新身份或重新配对 |
| 服务或 TLS 长时间无响应 | 自动回归在配置的恢复窗口内结束并明确报错 |
| 主动 disconnect 时服务离线 | 本地禁用立即生效，不因为随后恢复网络而自动启用 |

最终故障任务提交至重连后复验完成约为 Node 场景 7.47 秒、宿主场景 34.61 秒；这些时间包含预置 1.5 秒注入等待、退避轮询及查询，不是单纯 TCP 恢复耗时。未使用人工或脚本兜底启动服务，`manualRecoveryUsed:false`。原设备 ID 始终为 `e032c011-1a94-4882-887c-b8e9c62d1ce1`，计算机名 `qingwei`，正式服务地址仍为 `https://127.0.0.1:18766`。

测试脚本结束时主动关闭自己创建的设备监控进程和 TCP 代理；没有停止正式服务。服务健康探测不刷新输入控制租约，避免监控进程掩盖控制端失联。

本轮额外发现并修复两个问题：

- 助手 HTTP 响应按 Buffer 分块转字符串时，跨块中文可能变成替换字符并使输出字节数异常。改用 UTF-8 流解码，加入逐字节碎片测试。
- HTTPS 已就绪但用户助手尚未监听时，新用户命令可能立即失败。明确连接拒绝时最多等待 5 秒；已派发后丢失回复不重发，等待期间取消也不继续派发。

保留了中间失败记录：`01-54-51` 抓到助手启动空窗；`01-56-26` 的重连实际完成，但旧探针错误地要求“终止宿主的触发命令”必须为 unknown。该触发命令有时会在 Windows 完成进程树清理前成功落盘，属于合法成功；最终探针另外启动一条明确未完成的任务来验证 unknown，避免把合法完成结果误判失败。

最终 `npm test` 为 32 通过、0 失败、1 项真实服务集成默认跳过；另行启用的真实 CLI 集成在更新并重启的 SYSTEM 服务上通过。Skill 格式校验通过。这里验证的是 localhost 故障模拟、进程崩溃和 SCM 恢复；整机重启、物理网线/Wi-Fi 断开、LAN 地址变化与跨机环境仍需对应场景验收。
